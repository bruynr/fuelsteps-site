# Plan Builder v2 (12 steps, g-suffix, @-absolute, import string, FAQ) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Mirror the app's schema v2 in the web builder (12 steps, mandatory `g` carbs suffix, absolute `@` positions), add a one-paste import string with a copy button, and add two FAQ items (GPS drift advantage, chart shows planned values).

**Architecture:** All parsing/formatting changes go in `plan-core.js` (pure, tested with `node --test`); `plan.js` only gains an "at/after" select per step row and an import-string block. Content changes (FAQ, format reference) go in the 6 language `index.html`/`plan/index.html` pages and `llms-full.txt`.

**Tech Stack:** Vanilla ES modules, `node --test` (runs in the deploy workflow), static pages built per language (check `build.py` for how language pages are generated before editing them by hand).

**Spec:** The app-repo plan `app/docs/superpowers/plans/2026-10-02-schema-v2.md` ("Decisions" section) is the source of truth for the parser semantics. The builder must round-trip exactly what `ScheduleParser.mc` accepts after that plan lands.

## Global Constraints

- Site repo default branch is `gh-pages` (deploys on merge). Never commit to it directly; branch `feature/builder-v2`.
- Tests: `node --test plan-core.test.js` must pass; the deploy workflow runs it.
- Umami events carry names only, never schedule contents.
- New user-visible strings go in all 6 i18n files: `i18n/{en,nl,de,fr,es,it}.json`.
- Import format (must match the app byte-for-byte): `name;km|min;step;step;…`, separators `;` and newlines, blank segments skipped, unit token case-insensitive literal `km`/`min`.
- Practical Garmin Connect paste limit: 256 chars → warn above it.
- Commit messages: extremely concise; end with `Co-Authored-By: Claude Fable 5 <noreply@anthropic.com>`.

## Review Focus

1. A step with `abs` but a position at/behind the previous cumulative total → validation error, not a negative interval in the moments table (Task 1).

3. Import string of a 12-step schedule with long texts exceeds 256 → visible warning, copy still allowed (Task 3).
4. Old localStorage schedules (no `abs` key) load without errors — `fromJSON` must default `abs` to false (Task 1).
5. Steps 9-12 render, reorder and copy exactly like 1-8 (field list shows 12 rows) (Task 2).

```js
function renderImport(v) {
  const segs = importSegments(schedule);
  const text = segs.join(";\n"); // one segment per line; the app accepts ; and newlines both
  $("plan-import").textContent = text;
  const tooLong = text.length > LIMITS.importMax;
  $("plan-import-warn").textContent = tooLong ? fmt(S.warn_import_long, { max: LIMITS.importMax }) : "";
  $("plan-import-copy").onclick = (e) => {
    copyText(text, e.currentTarget);
    track("plan_copy_import", { unit: schedule.unit, steps: schedule.steps.length, len: text.length });
  };
}
```

- [ ] **Step 2: FAQ items (×6 languages, translated in each language's tone)**

English source:
- **Q: My alerts come slightly before the aid stations in a race. Why?** A: Your watch measures a little more distance than the official course (you never run the perfect racing line, and GPS wobbles). On a distance schedule set to the official aid-station kilometres, alerts therefore drift slightly *ahead* of the posts as the race progresses — which is exactly what you want: the reminder comes before you reach the table.
- **Q: What does the carbs chart in Garmin Connect show?** A: Planned intake. The chart and totals are labelled "(planned)": they record what the schedule said, not what you actually swallowed. Skip a gel and the chart won't know.
